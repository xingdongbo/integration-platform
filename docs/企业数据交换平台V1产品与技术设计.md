# 企业数据交换平台 V1.0 产品需求与技术设计文档

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 项目名称 | 企业数据交换平台 / Enterprise Integration Hub |
| 文档版本 | V1.0 |
| 阶段范围 | 第一阶段：基础可用版本 |
| 目标用户 | ERP、WMS、MES、WCS 等内部业务系统对接团队、接口维护人员、运维人员 |
| 技术方向 | Java 17、Spring Boot 3、MyBatis-Plus、MySQL、OkHttp、Vue3、Vite、Element Plus |

## 2. 项目背景

公司内部存在 ERP、WMS、MES、WCS、AGV 以及其他第三方系统。各系统之间存在大量接口交互，目前主要采用点对点对接方式，导致接口分散、重复开发、字段转换逻辑分散、异常难追踪、失败后缺少统一重试与补偿机制。

建设企业数据交换平台的目标，是将系统间接口交互统一收敛到一个可配置、可追踪、可重试的数据交换中枢中。

## 3. 平台定位与建设目标

### 3.1 平台定位

平台定位为企业内部系统之间的数据交换中枢，而不是单纯的接口配置工具。

```text
来源系统 → 数据交换平台 → 目标系统
```

平台统一负责：

1. 接收来源系统请求。
2. 保存来源系统原始报文。
3. 根据配置执行请求报文转换。
4. 调用目标系统接口。
5. 保存目标系统原始返回。
6. 根据配置执行响应报文转换。
7. 返回结果给来源系统。
8. 记录完整交换日志。
9. 接口失败时支持重试和人工补偿。

### 3.2 V1 建设目标

V1 目标是先完成稳定可用的数据交换能力，解决 ERP、WMS、MES、WCS 之间接口统一管理和数据交换问题。

V1 必须实现：

- 系统管理。
- 接口配置管理。
- Header 配置。
- 请求映射配置。
- 响应映射配置。
- 统一交换入口。
- 接口交换引擎。
- 交换日志记录。
- 接口测试。
- 失败人工重试。

V1 暂不实现：

- 多租户。
- 复杂流程编排。
- 可视化拖拽。
- API 网关。
- OAuth2。
- Kafka。
- ELK。
- SDK。
- FTP / SFTP / SOAP。
- 复杂权限体系。
- SaaS 化能力。

## 4. 核心业务模型

所有接口交换统一抽象为以下模型：

```text
SourceRequest
      ↓
RequestMapping
      ↓
TargetRequest
      ↓
CallTargetApi
      ↓
TargetResponse
      ↓
ResponseMapping
      ↓
SourceResponse
```

中文流程：

```text
来源请求
  ↓
请求映射
  ↓
目标请求
  ↓
调用目标系统
  ↓
目标返回
  ↓
响应映射
  ↓
返回来源系统
```

## 5. 典型业务场景

### 5.1 WMS 获取 ERP 入库单

业务方向：

```text
WMS → 数据交换平台 → ERP
```

处理步骤：

1. WMS 调用平台统一入口 `POST /exchange/WMS_GET_ERP_INBOUND`。
2. 平台生成 `traceId`，保存 WMS 原始请求报文。
3. 平台根据接口编码查询接口配置、Header 配置、请求映射配置和响应映射配置。
4. 平台将 WMS 请求格式转换为 ERP 请求格式。
5. 平台调用 ERP 入库单查询接口。
6. 平台保存 ERP 原始返回报文。
7. 平台将 ERP 返回格式转换为 WMS 标准响应格式。
8. 平台返回结果给 WMS。
9. 平台记录完整交换日志。

### 5.2 ERP 推送出库单到 WMS

业务方向：

```text
ERP → 数据交换平台 → WMS
```

处理步骤：

1. ERP 调用平台统一入口 `POST /exchange/ERP_PUSH_WMS_OUTBOUND`。
2. 平台生成 `traceId`，保存 ERP 原始请求报文。
3. 平台根据接口编码查询接口配置、Header 配置、请求映射配置和响应映射配置。
4. 平台将 ERP 出库单格式转换为 WMS 接口格式。
5. 平台调用 WMS 出库单接收接口。
6. 平台保存 WMS 原始返回报文。
7. 平台将 WMS 返回结果转换为 ERP 标准响应格式。
8. 平台返回处理结果给 ERP。
9. 平台记录完整交换日志，并在失败时支持人工重试。

## 6. V1 功能需求

### 6.1 系统管理

用于维护业务系统基础信息，例如 ERP、WMS、MES、WCS、AGV 等。

功能范围：

- 新增系统。
- 修改系统。
- 删除系统。
- 启用 / 停用系统。
- 查询系统列表和详情。

核心字段：

| 字段 | 说明 |
| --- | --- |
| system_code | 系统编码，唯一 |
| system_name | 系统名称 |
| system_type | 系统类型，如 ERP、WMS、MES、WCS |
| base_url | 系统基础地址 |
| status | 状态：启用 / 停用 |
| remark | 备注 |

### 6.2 接口管理

用于配置来源系统和目标系统之间的交换关系。

功能范围：

- 新增接口交换配置。
- 修改接口交换配置。
- 删除接口交换配置。
- 启用 / 停用接口。
- 查询接口列表和详情。

核心字段：

| 字段 | 说明 |
| --- | --- |
| interface_code | 接口编码，唯一，如 `WMS_GET_ERP_INBOUND` |
| interface_name | 接口名称 |
| source_system | 来源系统编码 |
| target_system | 目标系统编码 |
| target_url | 目标接口地址，可为绝对地址或相对目标系统 `base_url` 的路径 |
| method | 请求方式：GET / POST |
| content_type | 内容类型，V1 主要支持 `application/json` |
| timeout | 超时时间，单位毫秒 |
| status | 状态：启用 / 停用 |
| remark | 备注 |

### 6.3 Header 配置

用于配置平台调用目标系统时需要携带的请求 Header。

功能范围：

- 新增 Header。
- 修改 Header。
- 删除 Header。
- 查询 Header。

核心字段：

| 字段 | 说明 |
| --- | --- |
| interface_code | 关联接口编码 |
| header_name | Header 名称 |
| header_value | Header 值 |

示例：

```text
Authorization: Bearer xxx
Content-Type: application/json
```

### 6.4 请求映射配置

用于将来源系统请求转换为目标系统请求。

功能范围：

- 配置字段映射。
- 配置固定值。
- 配置默认值。
- 配置简单表达式。
- 按排序字段控制映射执行顺序。

核心字段：

| 字段 | 说明 |
| --- | --- |
| interface_code | 关联接口编码 |
| source_field | 来源字段路径，如 `orderNo`、`data.orderNo` |
| target_field | 目标字段路径，如 `billNo`、`data.inboundNo` |
| mapping_type | 映射类型：FIELD / CONST / DEFAULT / EXPRESSION |
| default_value | 默认值或固定值 |
| expression | 简单表达式 |
| sort | 排序 |

映射类型说明：

| 类型 | 说明 |
| --- | --- |
| FIELD | 字段映射，从来源字段读取值并写入目标字段 |
| CONST | 固定值映射，忽略来源字段，写入固定值 |
| DEFAULT | 默认值映射，来源字段为空时写入默认值 |
| EXPRESSION | 简单表达式映射，基于来源报文计算目标值 |

示例：

```text
WMS.orderNo → ERP.billNo
WMS.warehouseCode → ERP.whCode
```

### 6.5 响应映射配置

用于将目标系统返回转换为来源系统响应。

功能范围与请求映射一致，但映射方向为目标系统响应到来源系统响应。

示例：

```text
ERP.code → WMS.code
ERP.msg → WMS.message
ERP.data.orderNo → WMS.data.inboundNo
```

### 6.6 统一交换入口

V1 提供统一 HTTP 入口：

```text
POST /exchange/{interfaceCode}
```

示例：

```text
POST /exchange/WMS_GET_ERP_INBOUND
POST /exchange/ERP_PUSH_WMS_OUTBOUND
```

入口要求：

- `interfaceCode` 用于匹配接口配置。
- 请求体 V1 主要支持 JSON。
- 返回体为根据响应映射生成的来源系统标准响应。
- 每次请求必须生成唯一 `traceId`。

### 6.7 接口交换引擎

核心执行流程：

```text
1. 接收来源系统请求
2. 生成 traceId
3. 保存来源原始请求
4. 查询接口配置
5. 校验接口状态和系统状态
6. 执行请求映射
7. 保存目标请求报文
8. 调用目标系统接口
9. 保存目标系统原始返回
10. 执行响应映射
11. 返回来源系统
12. 保存完整交换日志
13. 失败时生成或更新重试任务
```

建议核心类：

| 类名 | 职责 |
| --- | --- |
| ExchangeController | 统一交换入口 |
| ExchangeService | 编排一次完整交换流程 |
| RequestMappingEngine | 请求映射执行 |
| ApiExecutor | 目标系统 HTTP 调用 |
| ResponseMappingEngine | 响应映射执行 |
| ExchangeLogService | 交换日志记录与查询 |
| RetryTaskService | 重试任务创建、查询和人工重试 |

### 6.8 交换日志

每次接口交换必须记录完整日志，覆盖成功和失败场景。

核心字段：

| 字段 | 说明 |
| --- | --- |
| trace_id | 链路追踪 ID |
| interface_code | 接口编码 |
| source_system | 来源系统 |
| target_system | 目标系统 |
| business_no | 业务单号，可从请求中提取或人工配置扩展 |
| source_request_raw | 来源系统原始请求 |
| target_request_data | 请求映射后的目标请求 |
| target_response_raw | 目标系统原始返回 |
| source_response_data | 响应映射后的来源响应 |
| status | 执行状态 |
| error_msg | 错误信息 |
| execute_time | 执行耗时，单位毫秒 |
| create_time | 创建时间 |

日志状态：

| 状态 | 说明 |
| --- | --- |
| RECEIVED | 已接收 |
| MAPPED | 已映射 |
| CALLING | 调用中 |
| SUCCESS | 成功 |
| FAILED | 失败 |
| RETRYING | 重试中 |

### 6.9 接口测试

后台提供接口测试页面，便于接口维护人员验证配置正确性。

功能范围：

- 选择接口编码。
- 输入 JSON 请求参数。
- 执行接口测试。
- 查看目标请求报文。
- 查看目标响应报文。
- 查看最终返回报文。
- 查看本次测试对应的 `traceId` 和交换日志。

### 6.10 失败重试

V1 实现基础人工重试能力。

功能范围：

- 失败日志可人工重试。
- 支持最大重试次数。
- 支持重试状态记录。
- 重试时复用原始来源请求和接口配置重新执行交换流程。

核心字段：

| 字段 | 说明 |
| --- | --- |
| trace_id | 原始交换链路 ID |
| interface_code | 接口编码 |
| retry_count | 当前重试次数 |
| max_retry_count | 最大重试次数 |
| last_error_msg | 最近一次错误信息 |
| next_retry_time | 下次可重试时间，V1 可为空或用于人工提示 |
| status | 状态：待重试 / 重试中 / 重试成功 / 重试失败 |

## 7. 非功能需求

### 7.1 可用性

- V1 支持单体部署，优先保证功能闭环。
- 关键执行过程必须有日志，便于问题追踪。
- 目标系统调用失败、超时、返回异常时，平台不能丢失来源请求和错误上下文。

### 7.2 性能

- V1 以同步 HTTP 调用为主。
- 单次映射处理应保持轻量，避免复杂脚本和重型流程编排。
- 接口配置可在服务层预留缓存扩展点，但 V1 可先直接查询数据库。

### 7.3 安全

- V1 暂不实现 OAuth2 和复杂 RBAC。
- Header 中涉及 Token、密钥等敏感信息时，日志展示应预留脱敏能力。
- 管理后台后续接入权限体系时，应控制配置修改和日志查看权限。

### 7.4 可维护性

- 交换流程按 Controller、Service、Mapping Engine、Executor、Log Service 分层。
- 映射逻辑与 HTTP 调用逻辑解耦。
- 数据库表结构与业务模型保持一致，便于后续扩展异步、路由、监控和告警能力。

### 8.1 V1 总体架构

```text

  │
  │ POST /exchange/{interfaceCode}
  ↓

  ↓

  ├─ 查询接口配置 / Header / 映射规则
```

## 9. 关键流程设计

### 9.1 正常交换流程

```text
来源系统请求
  ↓
生成 traceId 并记录 RECEIVED 日志
  ↓
查询并校验接口配置
  ↓
执行请求映射并记录 MAPPED
  ↓
调用目标系统并记录 CALLING
  ↓
保存目标系统原始响应
  ↓
执行响应映射
  ↓
记录 SUCCESS 日志
  ↓
返回来源系统响应
```

### 9.2 失败流程

```text
任意阶段发生异常
  ↓
捕获错误上下文
  ↓
记录 FAILED 日志
  ↓
创建或更新重试任务
  ↓
返回统一失败响应给来源系统
```

### 9.3 人工重试流程

```text
运维人员选择失败日志或重试任务
  ↓
校验 retry_count < max_retry_count
  ↓
状态置为 RETRYING
  ↓
使用原始请求重新执行交换流程
  ↓
成功：更新日志和重试任务为成功
  ↓
失败：增加 retry_count，记录 last_error_msg
```

## 10. 验收标准

### 10.1 功能验收

- 可维护系统信息，并支持启用 / 停用。
- 可维护接口交换配置，并支持启用 / 停用。
- 可维护接口 Header。
- 可配置请求映射和响应映射。
- 来源系统可通过 `POST /exchange/{interfaceCode}` 调用平台。
- 平台可根据配置完成请求映射、目标接口调用、响应映射。
- 每次交换均可查询完整日志，包括原始请求、目标请求、目标响应、最终响应、状态和错误信息。
- 接口测试页面可展示目标请求、目标响应和最终响应。
- 失败交换可人工重试，并记录重试次数和状态。

### 10.2 业务场景验收

#### WMS 获取 ERP 入库单

- WMS 调用 `POST /exchange/WMS_GET_ERP_INBOUND`。
- 平台完成 `WMS 请求 → ERP 请求 → ERP 返回 → WMS 返回`。
- 后台可查看完整交换日志。

#### ERP 推送 WMS 出库单

- ERP 调用 `POST /exchange/ERP_PUSH_WMS_OUTBOUND`。
- 平台完成 `ERP 请求 → WMS 请求 → WMS 返回 → ERP 返回`。
- 调用失败后可在后台执行人工重试。

## 12. 总结

V1 的核心价值是围绕“统一入口、统一转换、统一调用、统一日志、统一重试”构建企业内部数据交换闭环。第一阶段不追求大而全的 ESB 能力，而是优先落地 ERP、WMS、MES、WCS 等系统之间稳定可用、可追踪、可补偿的数据交换能力，为后续异步处理、条件路由、监控告警、权限管理和产品化能力打基础。
